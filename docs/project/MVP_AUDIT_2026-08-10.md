# Auditoría inicial del MVP — 10 de agosto de 2026

## Alcance de esta auditoría

Revisión documental y de estado del repositorio antes de iniciar el cierre del
MVP. La fuente de producto sigue siendo `docs/master/DOCUMENTO_MAESTRO.md`;
GitHub mantiene la fuente técnica y Notion el seguimiento operativo.

## Estado de referencia

- Repositorio: `buscohuella/buscohuella`.
- Último commit publicado revisado: `6790c90` — avatar de perfil y traducciones.
- Rama principal: `main`.
- Entorno probado por el fundador: aplicación web local con Supabase y Mapbox.
- Ámbito geográfico del piloto: Sabadell.
- Arquitectura prevista: web-first para el MVP; Expo móvil posterior, salvo
  aprobación explícita de un cambio de alcance.

## Funcionalidad validada hasta ahora

- autenticación, sesión, recuperación y protección de rutas;
- perfiles privados y públicos, alias, municipio y biografía;
- avatar de usuario: subida, reemplazo, eliminación, límite y Storage con RLS;
- mascotas: alta, edición, fotografías, archivado y estados;
- avisos perdidos y encontrados, borradores, publicación y ciclo de vida;
- prevención de avisos duplicados para una mascota con alerta abierta;
- fotografías reutilizadas desde la ficha de la mascota;
- avistamientos con fotografías y notificación al propietario;
- notificaciones internas, paginación de 10 y marcado inmediato como leído;
- archivado y resolución de avisos;
- mapa público, listado alternativo, círculos para ubicación aproximada,
  autocompletado y pin desplazable;
- selector geográfico reutilizado en avisos y avistamientos;
- español y catalán en los bloques migrados a i18n;
- lint, typecheck, build y tests ejecutados correctamente en las validaciones
  comunicadas, salvo incidencias puntuales ya corregidas.

## Inconsistencias documentales detectadas

1. `README.md` todavía describe la aplicación web y el backend como pendientes,
   aunque ya existe una implementación operativa.
2. `docs/frontend/FUNCTIONAL_DELIVERY_ROADMAP.md` mantiene estados antiguos en
   la sección de mapa, autocompletado y selector de ubicación.
3. `docs/product/MVP_IMPLEMENTATION_ROADMAP.md` y la página de Notion conservan
   la secuencia histórica como si el trabajo estuviera en FP-010/FP-011.
4. Notion contiene actualizaciones posteriores que no están completamente
   reflejadas en los estados resumidos iniciales.
5. El estado de la app móvil necesita mantenerse como posterior al MVP web
   mientras el Documento Maestro no cambie explícitamente.

## Riesgos y pendientes para cerrar el MVP web

### Prioridad P0 — bloqueo de release

- confirmar que el working tree local queda limpio tras consolidar los cambios
  de mapa, móvil web, avatar e i18n;
- ejecutar de nuevo lint, typecheck, build y tests sobre el conjunto final;
- comprobar en Supabase que todas las migraciones aplicadas tienen equivalente
  versionado y que las políticas RLS de perfiles, mascotas, reportes,
  fotografías, avistamientos y notificaciones siguen siendo correctas;
- verificar que no se expone ubicación exacta, contacto privado, token secreto o
  datos personales en respuestas, errores, logs o metadata pública.

### Prioridad P1 — calidad antes del piloto

- auditoría responsive móvil en Chrome, Brave, Safari iOS y Android;
- resolver o documentar el mapa vacío en LAN: Mapbox no admite restricciones por
  IP, por lo que el token local actual no representa todavía el entorno móvil
  real;
- pruebas de teclado, foco, zoom 200 %, lector de pantalla básico, contraste,
  reducción de movimiento y mensajes dinámicos;
- revisión completa de traducciones ES/CA y detección de textos visibles fuera
  del sistema i18n;
- revisar estados de carga, vacío, permisos denegados, errores recuperables y
  acciones duplicadas;
- revisar títulos, metadata, Open Graph, canonical, robots y rutas públicas;
- establecer una prueba manual reproducible por flujo y dos usuarios.

### Prioridad P2 — posterior o no bloqueante

- Web Push y alertas por proximidad;
- preferencias avanzadas de notificación;
- chat, QR/NFC, GPS continuo y app móvil;
- baja de cuenta, exportación y preferencias de privacidad avanzadas;
- observabilidad avanzada, rate limiting y moderación ampliada.

## Orden de trabajo propuesto

1. Sincronizar estados documentales y Notion con el código real.
2. Cerrar la auditoría de calidad web: responsive, accesibilidad, i18n y UX.
3. Revisar seguridad, privacidad, RLS, Storage y errores.
4. Ejecutar una matriz de pruebas manuales del MVP con dos cuentas y modo
   incógnito.
5. Corregir regresiones y repetir las validaciones técnicas.
6. Preparar el paquete de piloto de Sabadell y registrar las excepciones.
7. Decidir separadamente si la app móvil entra en el alcance del piloto; no se
   debe asumir que forma parte del MVP actual.

## Criterio de cierre

El MVP web estará listo para piloto cuando los P0 estén cerrados, los P1 tengan
resultado validado o excepción documentada, el conjunto de pruebas manuales
sea reproducible y GitHub, documentación y Notion describan el mismo estado.
